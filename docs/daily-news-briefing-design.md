# 每日热点新闻播报 · 需求分析与设计

> 目标：在 dsh-music-player 的「音乐 + AI 讲书」之上新增「新闻播报」：驱动 LLM 用 web search
> 收集当天头条（可分类别），整理筛选成口播稿，再用现有 TTS 管线合成语音，在播放条上播报。
>
> 状态：已确认（方案 A / 默认五类别 / v1 含定时）。实现里程碑见文末。

## 1. 需求分析

### 1.1 用户场景

1. **即时播报**：用户在对话框说「播报一下今天的新闻」→ agent 搜索当天头条 → 整理成简报 → 浏览器播放条语音播报。
2. **每日定时**：用户说「每天早上 9 点给我播报新闻」→ 创建每日定时任务，到点自动收集 + 播报。
3. **面板回看**：错过播报或想重听 → 播放面板新增「新闻」页签，按期次浏览、选择类别/条目播放；当天简报自动保留。

### 1.2 需求拆解 → 现状对照

| 需求环节 | 现有能力 | 结论 |
|---|---|---|
| LLM + web search 收集 | DSH agent 原生自带 `web_search` 工具（DeepSeek 搜索提供方），多轮多查询是模型强项 | **不新增基础设施**，用系统提示词驱动即可 |
| 分类整理筛选 | 模型在会话内完成（去重、按类归组、写口播摘要） | 同上，提示词约束输出格式 |
| 提交播报内容 | 插件已有 `ctx.tools.register()` 模式（`music_play`） | 新增一个 `news_broadcast` 工具接收结构化数据 |
| TTS 合成 | Host 端 `synthesizeCached()`（xiaomi MiMo → WAV，含 validateWav / 缓存 / 去重 / tts-logs 诊断） | **原样复用**，仅换缓存 key 前缀 |
| 语音播放 + 字幕 + 进度 | AI 讲书的分块播放器：`/book/<id>?from=n` 拉块、`/text?from=n` 字幕、`/meta` 章节结构、charOffsets 进度线、preload 双缓冲 | **复用同一套客户端播放机制**，新闻走平行路由 |
| 每日定时 | DSH `schedule` 插件：`schedule_create`（`at` 一次性 / `every` 固定频率，锚点对齐） | 用 schedule 承载「每日」，无需插件自建定时器 |

核心结论：**本功能 ≈ 讲书管线的「内容源替换」+ 一个提交工具 + 一段系统提示词**，架构上是低风险增量。

### 1.3 架构方案对比

**方案 A（推荐）：Agent 循环驱动 + DSH schedule 定时**

```
用户/定时提醒 → agent（会话内）
   ├─ web_search × N（按类别、带日期锚定）
   ├─ 去重 / 筛选 / 归类 / 写口播摘要          ← LLM 在环
   └─ news_broadcast 工具（结构化 JSON）
         └─ 插件 Host 端：校验 → 模板渲染口播稿 → 分块 → 持久化
               ├─ pendingIntent{kind:'news'} → 浏览器播放条开播
               └─ ~/.dsh/music-player-news.json（供面板回看）
```

- 优点：收集/整理质量最高（模型多查询、交叉验证、按时效筛选）；零新依赖；提示词集中一处；
  搜索过程在对话中可见、可纠偏；与 DSH「工具 + 会话 + schedule」的设计完全同构。
- 缺点：定时触发依赖会话 schedule 存活；浏览器需开着才出声（见 §7 降级）；定时运行消耗会话 token。

**方案 B（可选演进）：Host 端全自动**

插件注入 `web` 服务直接调 `ctx.web.search()`，再 `ctx.llm.stream()`（或纯模板）整理，自带 setInterval。
- 优点：不依赖会话与模型在环，可完全静默运行。
- 缺点：在插件里再造一个小型 agent（提示词/轮次/重试都要自己维护）；绕开 harness 的会话可观察性；
  搜索 provider 与 LLM provider 解析、鉴权、错误路径全部插件自理。
- 定位：仅当未来需要「脱离 DSH 会话独立运行」时再做，v1 不建议。

**方案 C：纯模板无 LLM 整理**——host 直接搜索结果拼稿，无整理筛选，不满足需求核心，仅作 B 的退化形态，不采纳。

## 2. 已确认决策

| 项 | 决定 |
|---|---|
| 架构 | **方案 A**：agent 用 `web_search` 收集整理，插件工具 `news_broadcast` 接收并播报 |
| 定时 | **v1 包含**。复用 DSH `schedule_create`：`every: 86400` 且 `scheduledAt` 锚定首个播报时刻（每日对齐触发）；**每日多班次 = 多条 schedule**（早/午/晚报）；班次级**勾选「收集后立即播放」（默认勾选）**，不勾选 = 静默收集；班次可**手动立即执行**；不用插件自建定时器（详见 §7） |
| 默认类别 | **热点（跨领域+热度排序，排第一） / 国内 / 国际 / 科技 / 财经 / 体育 / 娱乐**（用户可临时指定；全期 ≤20 条预算，热点优先 5~8 条） |
| 内容模型 | 期次（edition）→ 类别（category）→ 条目（title/summary/source/url） |
| 口播稿 | **插件端模板渲染**（开场白 → 类别引导语 → 逐条播报 → 结语），模型只产结构化数据，保证格式稳定、字幕与条目对齐 |
| TTS | 复用 `synthesizeCached` + `validateWav`，缓存 key `news:<editionId>:<chunkIdx>:<voice>`；声音复用 MIMO_VOICES，默认取 prefs |
| 播放复用 | 新闻期次 = 「虚拟书」：类别 → 章节（📖 目录即类别导航，next/prev 即上一类/下一类），字幕/进度线/断点续播全部继承 |
| 持久化 | `~/.dsh/music-player-news.json`，**只保留当天**：每日 03:00 + 启动时自动清理今天之前的期次/失败记录；当天之内每班次滚动保留最近 7 期 |
| UI | 播放面板新增大页签「新闻」；播放条新增新闻模式徽标 |

## 3. 数据模型与持久化

```jsonc
// ~/.dsh/music-player-news.json
{
  "editions": [
    {
      "id": "news-20260530-0900-a1b2",     // 日期 + 时间 + 随机后缀
      "originShiftId": "s2",               // 产出的班次 id；对话手动触发 = "manual"
      "title": "今日新闻播报",
      "date": "2026-05-30",
      "createdAt": 1750000000000,
      "voice": "白桦",
      "categories": [
        {
          "name": "国内要闻",
          "items": [
            { "title": "…", "summary": "…", "source": "新华社", "url": "https://…", "publishedAt": "08:02" }
          ]
        }
      ],
      "chunks": ["开场白…", "…"],           // 渲染+分块后的口播稿（播报原子）
      "charOffsets": [0, 118, …],           // 每块起始字符偏移（进度线用）
      "totalChars": 1024
    }
  ]
}
```

- 写入沿用 prefs 的 node:fs 直写模式（0600 不必须，非敏感；仍只存本地）。
- **保留策略：按任务（班次）分组滚动保留 7 期**——按 `originShiftId` 分组，每组各自裁剪
  最旧，互不挤占（否则高频静默班次会把低频班次的期次冲出窗口，如「每 2 小时收集 AI +
  每天 9 点综合早报」下早报活不过第二天）；已删除班次的历史组仍按 7 期自然老化。
  总量上界 ≈ (班次数 + 手动) × 7 期。单期条目上限：每类 ≤ 8 条、全期 ≤ 20 条。
  summary **不截断**：字数上限（建议 ≤ 200 字）只是提示词建议，agent 生成长度即最终
  长度，工具侧不做任何裁剪（`clipSummary` 已移除）；超长条目由分块按句边界切成多块
  播报，内容不丢。
- **每日过期清理（不再保留多天新闻）**：固定任务每天 **03:00** 后的首个检查点执行（30s
  轮询节奏与班次定时器一致、每自然日至多一次），**插件每次启动也立即检查一次**——两个触发
  点走同一入口 `purgeStaleNews`（`POST /dsh-music/news/purge-stale` 手动触发同一入口）：
  删除今天 00:00 之前的全部期次与失败记录（纯函数 `partitionStaleNews` 按 `createdAt`/`ts`
  分界），并联动销毁/归档其执行会话（与手动删除期次同一套联动）。按 createdAt 幂等，重复
  执行无副作用；⚠ 清理函数**不得**内部 `loadNews()`——内存态 news 是唯一活真相，飞行途中
  用磁盘快照覆盖内存会吞掉并发提交的期次（实测踩坑），调用方负责先 loadNews，变更段保持同步。
- **一个数据源、三种编排渲染**：结构化数据（categories → items）是唯一事实源——
  **口播稿**（模板：开场白/类别引导/逐条/结语，服务「听」）、**详情浏览**（类别分组单行
  摘要，服务「挑」）、**文字版**（文章模板：标题/元信息/类别小节/条目段落/尾注，服务
  「不方便听时直接读」）三个视图都由它渲染，互不另存、永不失同步。文字版渲染
  `categories/items` 而非 `chunks`（口播语的过渡语/开场白是冗余，阅读版不要）；
  item 的 `publishedAt` 为可选时间线索，阅读版来源行展示。
- **音频不落盘**：TTS 懒合成（播放到哪块合成哪块），产物只进内存 LRU 缓存（约 80 块，
  主机进程重启即清，复用 `ttsAudioCache` 机制）。文本已持久化，旧期次随时可重新合成播放；
  磁盘不膨胀，代价是重播旧期次需重新调用 TTS。「导出音频文件」留作未来演进。

## 4. 口播稿模板（插件端渲染）

```
【开场】您好，这里是今日新闻播报，{date}。           // 开场不再罗列类别，避免与类别引导重复
【类别】首先/接下来，将为您播报{类别名}方面的新闻。   // 仅多类别期次；**单类别不播引导**——开场
                                                    // （如「以下是今日国内要闻。」）已点名类别，
                                                    // 再接「将为您播报国内方面的新闻。」明显重复
【条目】第一条，{title}。{summary}。                 // 不附加「以上消息来自{source}」——来源只在详情/文字版展示
        （下一条起「接下来，」/「另外，」轮换衔接，避免机械感）
【结语】以上就是今天的新闻播报，感谢收听。
```

- 分块策略：按「一条新闻一个块」切分（每条 item / 其余引导语各成一块，**开场白与首个类别
  引导合并为一块**；单类别期次无引导语，开场白独占一块），块上限 ~400 字，保证字幕面板
  一帧就是一条完整新闻；合并开场可让播报更早进入第一条新闻、缩短后续长新闻的 TTS 预合成
  等待（新闻较长合成耗时，分块越多第一条越晚、停顿感越明显）；仅超长单元（>400 字，罕见）
  才在句边界内二次切分。
- 字幕对齐：每块一个字幕句，`/text?from=n` 返回该块原文；条目 ↔ 块的映射记入 `itemChunk[]`，
  供面板「点条目 → 跳到对应块」。单类别期次的 `categoryChunk[]` 指向首条条目起点——目录
  跳转/上下类导航直接落到该类第一条新闻。

## 5. Host 端新增

### 5.1 模型工具 `news_broadcast`

```js
{
  name: 'news_broadcast',
  description: '把整理好的当日新闻提交为语音播报（先自行用 web_search 收集并筛选后再调用）…',
  parameters: {
    title?: string,            // 默认「今日新闻播报」
    date?: string,             // 默认当天
    categories: [{ name, items: [{ title, summary, source?, url? }] }],  // 必填，≥1 类 ≥1 条
    opening?: string, closing?: string,   // 可选自定义开场/结语
    voice?: string,            // MIMO_VOICES 之一，默认 prefs
    autoplay?: boolean,        // 默认 true，推送播放条开播
    force?: boolean,           // 默认 false；冷却窗内跳过重复收集，true 强制新建
  },
  output: { editionId, categories, items, chunks, estMinutes, notice },
}
```

- execute 流程：校验规整 → **冷却窗去重** → 渲染分块 → 持久化 → `pendingIntent = { action:'play', kind:'news', id }` → 返回。
- **冷却窗幂等（防重复收集）**：同一 `originShiftId` 在冷却窗（默认 10 分钟）内再次提交
  → 不新建，返回 `{ skipped: true, existingEditionId, notice }`（notice 告知 agent 已跳过、
  可传 `force: true` 强制重收）。这同时兜住「连点立即执行」与「手动执行 × 定时触发撞车」
  两个方向的重复；`force: true` 为明确要求的逃生口（事件发酵中要多份快照）。
  同一会话 agent 运行天然串行，无并发写竞态；每任务 7 期滚动窗口是最后防线。
- **执行中状态上报（Host 统一设置）**：执行入口 `runCollection` 新建执行会话时由 Host 直接
  记录当前运行 `{ shiftId, sessionId, startedAt, scope }`（不再由 agent `begin` 上报）；完成时
  由 `news_broadcast` / `reportFailure` 自然清除。运行态带 TTL（10 分钟）懒过期（执行会话
  异常/漏报时自动复位）。面板经 `GET /dsh-music/news/runstate` 轻量轮询呈现（班次行 ▶ →
  ⟳ 收集中… 禁点、定时状态行显示「12:30 班次收集中…」），与冷却窗（挡"刚做完又来"）前后互补。
- `music_play` 的 pause/resume/stop/next/prev 是通用传输控制（next/prev 在讲书即跳章），新闻模式**免费继承**，不改 `music_play`。
- 系统提示词新增一节（order 116 旁）：说明新闻播报的使用方式——先按类别用 `web_search`
  多查询（带当天日期锚定）、跨源去重、只保留可确认时效的条目、每条写 120~260 字充实口播内容（讲清事件要点/背景/影响）并标注来源，
  再调 `news_broadcast`；用户指定类别则按用户类别，默认 `热点 / 国内 / 国际 / 科技 / 财经 / 体育 / 娱乐`
  中取 3~5 类（**热点排第一**：跨领域 + 热度排序，查询词用「今天 热搜榜 / 热点新闻」，来源为
  微博热搜、百度热搜、知乎热榜等聚合报道，条数预算优先 5~8 条；同一事件与领域类别重复时
  全期只出现一次，热点类保留领域外爆点或以「热度现象」角度呈现）；
  **也支持任意自定义主题（如 AI、新能源汽车）**——主题作为查询关键词组合搜索、并作为期次类别名，
  来源优先该主题的权威垂直媒体（见 §8.3 源引导）。

### 5.2 HTTP 路由（与 `/dsh-music/book/*` 同构）

| 路由 | 方法 | 作用 |
|---|---|---|
| `/dsh-music/news` | GET | 期次列表（id/date/title/类别名/条数），今日置顶 |
| `/dsh-music/news/\<id\>/meta` | GET | `{ total, sections(类别), charOffsets, totalChars, itemChunk[] }` |
| `/dsh-music/news/\<id\>/text?from=n` | GET | 第 n 块字幕文本 |
| `/dsh-music/news/\<id\>?from=n&voice=` | GET | 第 n 块 WAV（懒合成 + 缓存，同讲书） |
| `/dsh-music/news/\<id\>` | DELETE | 删除某期 |
| `/dsh-music/news/play` | POST | 面板「播放该期」→ 设 pendingIntent |

懒合成（点哪块合成哪块 + preload 预取下一块）而非开播前整期合成：首响快、失败影响面小、缓存可控。

## 6. Web 端新增

- 面板大页签行追加「新闻」：
  - 期次列表（「今天 · 09:00 已生成」徽标）→ 点进显示类别分组条目（title + source，summary 摘要行）；
  - 每条目可点：跳到对应块播放；类别头可点：从该类第一块播；顶部「▶ 播放整期」。
- 播放条：当前 `kind:'news'` 时显示「新闻播报」徽标；📖 目录按钮自然变为**类别目录**；
  字幕逐句滚动与全书进度细线（按已读字符）直接复用。
- 刷新续播：prefs 里已存 `playback`（当前曲目/进度），news 期次同结构接入即可。

## 7. 收集与播报时机（触发模型）

> 核心原则：**收集与播放是两件事**。收集永远产出一期（期次持久化、入列表）；
> 播放是收集之后的独立动作，由触发来源的配置决定是否自动执行，且随时可以从
> 面板对待播期次手动补播。

### 7.1 触发来源

| 触发 | 方式 | 收集时机 | 播报行为 |
|---|---|---|---|
| 手动（对话） | 「播报今天的新闻」 | 立即 | **收集完立即播放**（对话触发恒 `autoplay:true`） |
| 手动（对话，仅收集） | 「收集一下今天的新闻，先别播」 | 立即 | 不播，期次标「待播」 |
| 每日定时 | `schedule_create`（`every: 86400` 锚定时刻） | 每天到点 | 由班次勾选「收集后立即播放」决定（默认勾选 = 播） |
| 每日多班次 | 见 §7.2 | 各班次到点 | 各班次各自的勾选决定 |
| **手动立即触发定时规则** | 面板定时编辑器班次行「▶ 立即执行」（复制指令发 agent）；或对话「立即按晚班规则收集播放」 | 立即 | 按该班次的勾选决定 |

- **无常驻后台爬虫**：所有收集都发生在上述离散的 agent 运行里，每次触发都是一场新鲜
  `web_search`（按当时时点拉最新头条），保证时效；同时意味着**每次收集 = 一次真实 agent
  运行（搜索 + 整理 + TTS），班次越多成本越高**。
- **收集在主机进程后台完成，无需前台**：`ScheduleRuntime` 挂在 DSH 主机进程（process-local
  的 timer 驱动），浏览器/GUI 开不开、用户是否在场都不影响触发与收集；唯一前提是电脑开机且
  DSH 主机进程在运行。可见性上，收集过程写入会话事件日志——GUI 开着可实时旁观（可打断纠正），
  没开则静默完成事后可查。
- **错过补跑**：主机进程未运行而错过的触发，重启后由 `dueDecision` 计算最新一个错过的锚点
  occurrence 补跑**一次**（不逐个补齐错过的 N 次）。
- **播放静默 ≠ 收静静默**：`autoplay:false` 班次连 TTS 都不发生（懒合成在播放时才按块进行），
  静默收集的成本只有搜索 + LLM 整理。
- **浏览器未开不影响收集**：到点照常生成期次并持久化，仅播报不出声；面板「待播」徽标回看（见 UI 文档）。
  播报 intent 带 2 分钟时效——浏览器长时间未取则过期丢弃，不会在用户几天后打开页面时
  突兀地自动播放旧简报（音乐/讲书 intent 无时间戳，行为不变）。

### 7.2 每日多次的三种模式

班次的播放行为统一为**勾选式**：每个班次一个「收集后立即播放」勾选框，**默认勾选**；
不勾选 = 静默收集（`autoplay:false`，只生成期次不出声，进入待播列表）。

1. **多班次制（推荐）**：N 个时刻 = N 条 schedule，每条 `every: 86400` 锚定各自时刻
   （如 08:00 / 12:30 / 18:00 三条）。期次标题由 Host 确定性命名为**「M月D日 HH:MM 新闻播报」**
   （班次触发的提交覆盖 agent 传入的 title，不依赖 agent 自觉——无约束时每次执行的全新
   agent 会即兴起名，列表风格漂移；对话直接播报保留 agent 命名），期次列表按「今天 · HH:MM」自然排列。
   **每个班次可独立指定收集范围**：预设类别（国内/国际/科技/财经/体育/娱乐）chips + 自定义主题
   自由 tag（如「AI」「新能源汽车」，每班次 ≤ 5 个）；范围必填（至少一个类别或主题，
   新班次默认不选、选后方可保存；「全局默认类别」已退役）。**范围是硬约束**：触发指令
   会明确允许提交的类别名（scope.categories ∪ 自定义主题），`news_broadcast` 工具层
   校验提交的 categories——范围外类别整体过滤并在通知中说明，全部越界则拒绝生成。
   主题词双重语义：**搜索关键词**（「日期 + 主题 + 新闻」组合查询）与**期次类别名**
   （期次里出现以主题命名的类别）——例如「12:30 只收集 AI」的班次期次类别列只有 AI，
   标题仍为统一的「M月D日 12:30 新闻播报」。
2. **固定频率 + 时段守卫**：「每 4 小时一次」= 一条 `every: 14400` 锚定 08:00。注意 `every`
   会**全天候触发**（含凌晨），schedule 不支持 cron 式「仅白天」；解法是提醒词带守卫：
   *「若触发时刻不在 08:00–22:30，跳过本轮，不搜索不播报」*。省 schedule 数量，代价是
   夜间留下跳过记录。
3. **收集与播报解耦（静默收集）**：部分班次不勾选「收集后立即播放」（如每 2 小时的高频
   班次只收集），低频班次才播报。适合「随时点开面板都看到最新头条，但只在早晚听」。
   也可对话单独触发仅收集（`autoplay:false`）。

### 7.3 收集失败的处理流程

收集跑在主机侧（DSH 进程内 agent），「断网」指主机断网；仅浏览器离线不影响收集。
**失败原因不做诊断、只透传现象**：agent 无从判断是断网还是搜索服务端故障，`reason`
一律记录工具返回的**错误码 + 消息摘要**（如 `WEB_PROVIDER_UNAVAILABLE`、
`timeout after 30000ms`、`502 bad gateway`），面板展示原文 + 通用排查指引
（检查搜索提供方状态 / API key / 稍后重试），不给推断性结论。

触发后按现象分流：

```
定时触发 → agent 收集
 ├─ 搜索成功但 0 条结果 → 换查询词重试 2~3 次（有意义的重试）
 │    仍 0 条 → 记「无结果」（不算故障），本期次不生成
 ├─ 工具调用报错（provider 挂 / 超时 / 鉴权失败）
 │    → 短间隔确认性重试 1 次，仍失败立即放弃（基础设施故障重试无意义，不浪费 token）
 │    → 本期次不生成 —— 宁缺毋假，绝不用旧数据顶替
 │    → news_schedule {action:'reportFailure', kind:'error', reason:<错误码+消息摘要>}
 │      → Host 失败日志（prefs，最近 10 条）
 │    → 会话里向用户说明失败
 ├─ 部分类别失败 → 只提交成功类别（≥1 条即出一期），notice 注明失败类别
 └─ 成功 → 正常流程
```

- **不自动补收（v1 默认）**：本轮失败后下次触发即下一班；恢复靠面板班次行「▶ 立即执行」、
  或对 agent 说「补收早上那班」。
- **可选自动补收（提醒词模式，默认关）**：提醒内容可含「失败则 `schedule_create` 一个
  2 小时后的一次性 `at` 补收任务（最多重试 1 次）」——利用 agent 的自建 schedule 能力。
- **面板可见性**：定时状态行下方展示最近失败，文案直接透传现象——
  「⚠ 今天 12:30 班次收集失败 · 502 bad gateway ▶ 补收」/「⚠ 12:30 收集无结果」，
  用户无需翻会话即可知情与补收（见 UI 文档 §8）。

### 7.4 多次收集的内容组织

- **每班次独立成期，不合并进同一期**：音频一经生成不可变——往「今日简报」滚动追加条目会让
  正在播的期次内容漂移、字幕/条目↔音频块映射失效。
- 跨班次去重由每轮搜索的时效筛选自然完成（早报过的不再是「新」头条）；提醒词可附
  「与早间班次重复的仅保留重大进展」。
- **同一班次的重复触发由工具层冷却窗收敛**（见 §5.1）：冷却窗内重复提交 skip 不出新期，
  会话里由 agent 说明；`force:true` 才新建。

### 7.5 定时管理

### 7.5 定时管理（Host 自维护）

- **定时器由插件在 DSH 主机进程内自维护**（`rebuildTimer`：读 `schedulePrefs.shifts`，
  Node `setInterval` 每 30s 检查，到点触发 `runCollection`），**完全脱离会话存活**——不再
  依赖 DSH 会话级 schedule，会话销毁不影响每天到点触发；宿主重启后按持久化偏好自动重建。
  **保存即生效**，无需 agent 创建/同步 DSH 定时任务。
- **配置入口**：面板「⏰ 每日定时」规则编辑器按班次配置（预设类别 chips + 自定义主题 +
  「收集后立即播放」勾选 + 新闻采集模型，见 UI 文档 §4）；也可对 agent 说「每天早 8 点播
  AI 新闻」让其引导配置（范围信息存进 `schedulePrefs`，由面板保存后生效）。
- **一次执行 = 一个执行会话**：每次执行（定时到点 / 面板「▶ 立即执行」`run-now`）都经统一
  入口 `runCollection` **新建一个独立「执行会话」**（`ctx.agents.create`，模型取面板「新闻
  会话模型」选择器或当前活跃会话），上下文干净聚焦、互不干扰，不再有常驻复用会话。
  **会话命名 = 创建时间 + 任务类别**：`runCollection` 计算 `MM-DD HH:mm 类别`，创建成功后经
  `ctx.sessionTitle.rename(session, name)` 显式命名（如 `05-30 08:00 科技 + 主题:AI`）。
  ⚠ 不能用"首条消息前缀"自动命名——注入的 followup 是 `plugin` 来源，不满足 `session-title`
  的 `user` 资格，无法自动生成标题（实测踩坑），必须显式 `rename`。
- **会话归入「新闻收集」命名工作区**：DSH 工作区（workspace registry）按「账本登记 + 会话
  header cwd === 工作区路径」双重校验成员资格，插件直建的会话从不 attach，因此全部挂在
  「未分组」。修复：执行会话的 cwd 指向专属目录 `~/.dsh/news`（尊重 `DSH_HOME`，创建后取
  realpath 规范路径——工作区路径与 header cwd 都用这套规范比对），创建成功后
  `ctx.workspaceRegistry.create(dir, '新闻收集')`（幂等，同路径返回既有实体）+
  `ws.attachSession(sessionId)`，会话即归入侧边栏「新闻收集」分组（分组名可在 GUI 重命名）。
  任一步失败都吞掉（best-effort，分组失败不影响收集）。
- **结果与会话一一对应**：`news_broadcast` 上报时把当前执行会话 id 写入期次（`sessionId`），
  失败记录同样绑定；**删除某期新闻时联动清理它对应的执行会话**（`execSessions` 表持有
  `AgentHandle`，DELETE 时 `dispose` 并清映射）。
  ⚠ **DSH 没有「删除持久化会话」的 API**：`AgentHandle.dispose()` 只拆内存里运行的 agent
  （停止循环/注销），会话的 JSONL 持久化文件是只追加、从不删除的，重启后会被重新加载而再次
  出现。因此删除期次时除 `dispose`（本进程句柄优先，跨重启走 `resume→dispose` 兜底）外，
  还必须调用 **`ctx.workspaceRegistry.archiveSession(sessionId)`** 把该会话「归档」——归档集合持久化在
  storage domain（重启不丢），UI 对归档会话在会话列表/分组/搜索里一律隐藏，从而实现「删除新闻
  后对应执行会话从会话列表彻底消失且跨重启保持隐藏」。
  ⚠ 服务名是 `workspaceRegistry` 而非 `workspace`（实测踩坑：`ctx.get('workspace')` 返回
  `undefined`，归档静默失效；按 `archiveSession` 能力判定并兼容旧名兜底）。
  **关键：创建执行会话时必须在 `setup` 里 mount 默认 standing preset**
  （`agentPresets.mount(agentCtx)`，`meta.agentPreset` 记录 resolved id）——`web_search`/
  `web_fetch` 等工具是随 preset 按会话装配的，不 mount 的裸会话只有插件全局注册的
  `music_play`/`news_broadcast`/`news_schedule`，会因缺 `web_search` 而无法收集（实测踩坑）。

## 8. 数据来源与抓取机制

### 8.1 抓取发生在 agent 运行时，插件不写抓取代码

抓取全部发生在会话循环内，由 DSH 原生 web 工具完成（已核对 harness 源码的真实能力）：

| 工具 | 能力 | 角色 |
|---|---|---|
| `web_search`（主通道） | 一次调用 1~4 条查询；返回 `content`（聚合摘要）+ `sources[]`（`{url, title, snippet, publishedAt}`） | 按类别分批搜索；sources 即引用来源 |
| `web_fetch`（补充通道） | 抓单 URL 的 HTML/正文（30s 超时、20 万字符截断） | 重点条目取全文核实；摘要不足时补素材 |

底层为 DeepSeek 搜索提供方（Anthropic 兼容 Messages API，服务端联网搜索）——已配置 DeepSeek
提供方的环境天然可用，零新增配置。

### 8.2 查询策略（提示词驱动，而非代码写死）

系统提示词教给模型一套方法论：**按类别分批、每批 1~4 条查询、全部带当天日期锚定**
（如「5月30日 国内要闻 头条」「5月30日 科技新闻 36氪 IT之家」）。

模型对搜索结果执行质量控制流水线（全部模型在环）：

1. **时效筛选**：`publishedAt` / 正文时间线索确认「今日」才保留，存疑即弃；
2. **跨源去重**：同一事件多源报道只留一条，取最权威源；
3. **重要性排序**：每类 ≤ 8 条、全期 ≤ 20 条；
4. **写口播内容**：中性转述，**建议 200 字以内**（仅为建议——代码不截断，生成长度即播报
   长度，超长条目由分块按句边界切成多块、内容不丢），必标 `source` + `url`；
   **摘要须自含主语**——口播模板为「序号 + 摘要」，条目标题不参与播报（只在面板列表
   展示；曾尝试「序号 + 标题 + 摘要」，摘要导语复述标题会同一句连播两遍），摘要开头
   必须点明「谁/什么事」，让听众不看面板也能听懂。

### 8.3 数据源引导

不固定爬指定站点（那是 host 全自动方案的做法），由搜索聚合天然覆盖全网（DeepSeek 搜索后端
的全网索引），提示词仅引导**来源优先级**——要求每条必标来源、优先官方与该类别权威媒体：

| 类别 | 优先源（提示词清单） |
|---|---|
| **热点**（跨领域 + 热度排序） | 微博热搜、百度热搜、抖音热点、知乎热榜、今日头条热榜的**聚合报道**（榜单本身多登录墙/反爬，经搜索索引获取）；查询词「今天 热搜榜 / 热点新闻」；按热度排序，标榜单位（如「微博热搜」） |
| 综合/国内 | 新华社、人民日报、央视新闻、澎湃、光明网 |
| 国际 | 参考消息、环球网、CGTN（外电中文报道经上述渠道） |
| 科技 | 36氪、IT之家、少数派、TechCrunch |
| AI（主题） | 机器之心、量子位、新智元、36氪 AI（搜索自然带出垂直源，引导优先） |
| 财经 | 财新、第一财经、华尔街见闻、证券时报 |
| 体育 | 央视体育、懂球帝、虎扑、新浪体育 |
| 自定义主题 | 无固定清单——搜索自然发现，提示词要求「优先该主题权威垂直媒体、必标来源」 |

- 反爬导致 `web_fetch` 失败时由 agent 自行换源，插件不处理。
- ⚠ **fake-ip 代理环境的 `WEB_BLOCKED_URL`（实测踩坑）**：本机开 TUN 代理的 fake-ip DNS
  模式（Clash/mihomo、sing-box）时，所有域名都解析成 `198.18.0.0/15` / `fdfe:dcba:9876::/48`
  的代理内部地址，DSH `web_fetch` 的防 SSRF 保护（解析结果含非公网地址即拒绝）会对**所有**
  域名报错。插件层无法修改该工具（属 `dsh-web-fetch-http` 本体），因此提示词指引收集器：
  正常流程仍用 `web_fetch` 抓原文（每类挑 1~3 条权威来源）；单条报错确认性重试 1 次仍失败
  即放弃抓取、降级以 `web_search` 摘要继续，本会话后续条目不再尝试——不影响期次生成、
  不走失败上报；README FAQ 告知用户把代理 DNS 改为真实 IP 解析（`redir-host` /
  去掉 `fakeip`）即可恢复 `web_fetch`。
- **诚实边界**：源质量受搜索后端索引时效限制（无 `publishedAt` 的条目时效存疑即弃）；
  不抓登录墙内容（微博/公众号正文等）；小众垂直站可能不被索引覆盖。

### 8.4 模型与提供方选取（三个模型位，三种机制）

| 角色 | 选取机制 | 固定 DeepSeek？ |
|---|---|---|
| 收集/整理 LLM（搜索/筛选/去重/摘要） | **会话当前模型**（方案 A 的定义：驱动工具的 agent 本身） | 否——跟随会话模型，插件零感知零配置 |
| 搜索提供方（`web_search` 底层） | harness web 服务注册表（配置偏好 id → `available()` 可用性解析），当前内置 DeepSeek 搜索提供方 | 当前事实上是；属 harness 层，插件无关，未来换提供方零改动 |
| TTS 提供方（语音合成） | 插件既有 `resolveTts`：`listProviders()` + settings.yaml 按 `xiaomi/mimo` 关键字匹配，`MIMO_API_KEY` 环境变量兜底 | 是（MiMo，与讲书共用同一解析与声音表） |

- 收集/整理不设「新闻专用模型」配置，也无处可配；口播稿为插件端模板渲染（不过 LLM），
  整条链路的 LLM 成本 = 会话模型的一轮多轮运行。
- 搜索可用性取决于 DeepSeek API key 是否已配置，与会话用哪个模型无关。
- 唯一需要插件自选模型的场景是方案 B（host 全自动，M4）：届时收集 LLM 由插件直调
  `ctx.llm.stream()`，选取逻辑可照搬 `resolveTts` 的关键字匹配模式做成配置项。

### 8.5 兜底（可选演进，M4）

`web_search` 未配置或故障时，v1 直接降级提示。预留兜底：插件 Host 端直取公开热榜聚合 API
（今日热榜 / 「60秒读懂世界」类 JSON 端点，无需 LLM），作为降级源或「零成本快速模式」；
均为非官方接口，只作兜底不作主路。

## 9. 边界与降级

| 场景 | 处理 |
|---|---|
| 未配置 xiaomi TTS | 期次照常生成可阅读（面板可看全文），工具 notice 提示配置后可播 |
| `web_search` 不可用/无结果 | 见 §7.3：换词重试 → 仍失败不生成期次（宁缺毋假）、`reportFailure` 回写面板、会话说明；部分类别失败则只提交成功类别 |
| 单块 TTS 失败 | 沿用讲书：校验失败即报错该块、自动重试一次、tts-logs 可诊断 |
| 浏览器自动播放拦截 | 沿用「点 ▶ 解锁」文案 |
| 条目超限/字段缺失 | 工具侧硬校验：截断/丢弃并回写 notice，不让模型格式抖动破坏播报 |
| 内容合规 | 提示词要求中性转述、必标来源、不做猜测性推断；免责文案入 README |
